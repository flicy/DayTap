## 0. 开场钩子（约 2 分钟）

- 钩子一句话：我天天在 Apple Watch 上被 Grok Bot 推送刷屏——推送有了，指挥还没有。
- 群聊现场感（2026-11-03～11-04）：
  - Anatole：期待 Personal Agent / Grok Bot 在 Watch 上指挥。
  - 云飞扬：Watch 录音自动上传 → 手机实时 PPT / 决策表。
  - Jack：要的是完整真实个人数据，需求预测才能反推供给侧。
  - `.`：接 Grok 语音 API + skill，不同角色切 bot。
- 点名对标：Puppet 公众号文《七天时间…把 Apple Watch 变成最好的 AI 录音硬件》。
- 收束到今晚问题：录音硬件有人做了；「录完之后谁指挥、沉淀成什么」还空着。

## 1. 问题定义（约 2 分钟）

- 痛点不是「能不能录」，是「录了之后进不了自己的 Agent」。
- 三个断层（短句）：
  1. Watch 推送 ≠ Watch 指挥（已有推送；指挥待验证）。
  2. 录音文件 ≠ 可复用语料库。
  3. 单次转录 ≠ 实时决策表 / PPT。
- 我们周五要对齐的，是流水线边界，不是炫技 Demo 满分。

## 2. 方案总览（约 4 分钟）

结论：手机主力录音，Watch 只做 backup；按需录、按天同步；得到做转录；沉淀文档语料库；接 Grok Bot 出决策表/PPT；角色可切 bot。

| 环节 | 当前口径 | 状态 |
|------|----------|------|
| 主录音 | 手机 | 方案已定；端到端待验证 |
| Backup | Apple Watch | 方案已定；稳定性待验证 |
| 触发 | 按需录音（非全天候） | 口径已定 |
| 同步 | 按天整理 | 流程待验证 |
| 转录 | 得到 | 接入与质量待验证 |
| 沉淀 | 文档语料库 | 结构待验证 |
| Agent | Grok Bot → 决策表 / PPT | 实时性待验证 |
| 多角色 | 切换不同 bot | 产品设想；待验证 |

一句话差异化（对 Puppet）：  
他证明 Watch 能成为「最好的 AI 录音硬件」；我们要把录音接到 Personal Agent，变成「可指挥、可沉淀、可按角色切换」的日常入口。

## 3. Demo / 走查步骤（约 5 分钟）

> 原则：只演示已发生或可现场点开的；做不到的环节口头标「待验证」，不演假闭环。

建议走查顺序（可按周五前实际进度删减）：

1. **场景口述**（30s）：一场会议 / 一场访谈——为何按需开录，而非全天录。
2. **手机主录**（1 min）：展示开录入口与文件落盘位置（若周五前未跑通 → 用空流程示意 + 标待验证）。
3. **Watch backup**（1 min）：说明 backup 何时介入（信号差 / 手机不便）；不夸大「Watch 单机扛一切」。
4. **按天同步**（1 min）：展示「一天一包」整理逻辑（文件命名 / 文件夹约定）；自动化程度标待验证。
5. **得到转录**（1 min）：展示一份真实或样例转录进语料库的路径；质量对比待验证。
6. **Grok Bot 出口**（1–1.5 min）：
   - 理想路径：语料 → Bot skill → 决策表 / PPT 草稿。
   - 若实时未通：演示「非实时」喂文本出表，并明确：实时上传生成 = 待验证。
7. **切 bot**（30s）：口述多角色（例如会议纪要 bot / 商机判断 bot）；切换机制待验证。

## 5. 开放问题（约 2 分钟）

抛给听众，方便 Q&A 与后续共建：

1. Watch 上「指挥 Bot」最小闭环该是语音、表盘按钮，还是只做通知回传？（Anatole 期待点）
